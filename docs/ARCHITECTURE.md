# Архитектура

## Из чего собрано

```
saturday_tracker/
├── tracker_store.py        ядро: чтение и запись файлов, локи, git
├── tracker_ui.py           HTTP-сервер: отдаёт фронт и данные, принимает правки
├── tracker_mermaid.py      генерация диаграмм из данных
├── tracker_write_patch.py  патчи записи для собранного фронта
├── tracker_selftest.py     самопроверка с негативным контролем
├── ctx_lock.py             межпроцессный мьютекс
├── static/                 собранный фронт и mermaid
└── sample_data/            демо-тикеты для первого запуска
```

Зависимость одна и однонаправленная: `ui` → `store`. **UI ничего не пишет сам** —
вся запись живёт в `store`, чтобы её можно было тестировать без сервера
и чтобы правило «сначала лок, потом запись» нельзя было обойти по невнимательности.

## Запись: почему так осторожно

Порядок гарантий в `store`:

1. **Лок** (`ctx_lock.py`) — атомарный `mkdir` в каталоге локов. Выбран `mkdir`,
   а не файл-флаг: создание каталога атомарно на всех POSIX-системах и не требует
   отдельной библиотеки. Лок протухает по TTL, если процесс-владелец умер.
2. **Атомарная подмена** — `os.replace` временного файла. Читатель никогда
   не видит половину файла.
3. **fsync** до подмены — иначе «сохранено» означает лишь «в page cache»,
   и внезапная перезагрузка съедает правку, о которой UI отчитался успехом.
4. **git-коммит** — если каталог данных под git.

Проверено нагрузкой: 8 одновременных писателей в один CSV не нарушают
целостность — все правки применяются последовательно, битых строк нет.

## Фронт: собранный бандл и патчи

`static/tracker_app.html` — самодостаточный бандл (React и mermaid вшиты).
Исходников бандла в репозитории **нет**, и это стоит назвать прямо: пересобрать
его отсюда нельзя.

Правки во фронт вносятся `tracker_write_patch.py` — он находит в бандле
оставленные автором точки-заглушки и подменяет их вызовами API. Замены
адресные, по строкам-маркерам.

**Что будет, если бандл пересоберут и маркеры изменятся.** Сервер не отдаст
молча «рабочий» интерфейс, который ничего не сохраняет: он напечатает, какая
именно замена не сработала. Этот же класс ошибок ловит селфтест поимённо
по всем точкам записи.

Ограничение осознанное: бандл — это ~85% вендорного кода, его пересборка
требует тулчейна, которого в проекте нет. Если фронт понадобится развивать,
правильный шаг — вынести его исходники в отдельный подпроект, а не наращивать
патчи.

## Данные отдельно от кода

Каталог тикетов задаётся `--data`, переменной `SATURDAY_TRACKER_DATA` или
берётся как `./tracker`. Приложение версионируется здесь, тикеты — в вашем
проекте. Смешивать их в одном репозитории не нужно: код обновляется из
upstream, данные остаются вашими.

## Почему нет базы данных

Развилка обсуждалась и решена в пользу файлов. Аргументы:

- **Diff и merge.** Правка тикета видна в code review; две ветки сливаются git-ом.
- **Чтение без API.** Агент делает `grep` — не нужен ни клиент, ни слой доступа.
- **История бесплатно.** Аудит правок — это git-лог, а не таблица, которую надо
  проектировать и заполнять.
- **Нечего эксплуатировать.** Ни сервера, ни миграций, ни бэкапа сверх git.

Где выбор изменится: многопользовательская конкурентная запись из разных сетей,
десятки тысяч тикетов, запросы вида «покажи всё, что меняло статус дважды
за неделю». Тогда правильный шаг — SQLite или Postgres как хранилище при том же
интерфейсе `store`, а не переписывание всего.

## Самопроверка

`tracker_selftest.py` проверяет восемь классов инвариантов — от экранирования
подписей mermaid до того, что фронт получает живые данные, а не вшитый снапшот.

Ключевое свойство: **у каждого класса есть негативный контроль**. Проверка
прогоняется на заведомо испорченных данных и обязана покраснеть. Зелёный тест,
который не умеет краснеть, не доказывает ничего — это правило появилось после
реального случая, когда «все тесты зелёные» сочеталось с неработающим фронтом.
